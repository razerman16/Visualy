# Revue de sécurité Screnzly — 27 octobre 2026

Référence du code : `809a3e8b1cb058c91d813cf756f8f55836e7039d`.

## Conclusion

Des corrections sont nécessaires avant un usage sur un réseau partagé ou avec des comptes éditeurs peu fiables. Le réseau local ne protège pas contre l’interception, un poste compromis ou un utilisateur interne malveillant. Aucun contournement complet de l’authentification ni exécution de code arbitraire n’a été démontré pendant cette revue.

Cette revue couvre le code API, administration, lecteur, stockage hors connexion, dépendances npm, Docker, reverse proxies, initialisation, sauvegarde et restauration. Elle associe analyse statique et vérifications ciblées non destructives. Elle ne constitue pas une certification ni un pentest exhaustif de l’installation utilisateur.

Les constats sont classés par priorité : P1 à traiter avant déploiement sur un LAN partagé ; P2 à traiter ensuite. La gravité dépend des prérequis précisés. Aucun correctif applicatif n’a été appliqué pendant cette revue.

## Constats

### S01 — P1 — HTTP et cookies non sécurisés par défaut

**Sources :** `compose.yaml:28,50,67`, `scripts/init-env.sh:26`, `apps/api/src/index.ts:37`.

Le lancement standard publie les deux interfaces sur toutes les adresses en HTTP, avec `COOKIE_SECURE=false`. Les mots de passe, cookies de session et jetons des lecteurs transitent sans chiffrement. Un acteur capable d’intercepter ou modifier les échanges LAN peut récupérer une session ou altérer le contenu reçu. Le contrôle SHA-256 des médias ne garantit pas l’authenticité si le manifeste peut lui aussi être modifié sur le réseau.

**Preuve :** les deux interfaces locales répondent en HTTP sur 8080/8081 ; la configuration rend ce mode accessible sur le réseau. Aucun trafic utilisateur n’a été capturé.

**Correction :** utiliser `compose.https.yaml` avec certificats approuvés, supprimer les ports HTTP directs comme le fait cet override, activer Secure et documenter HTTPS comme configuration normale. Restreindre l’administration par pare-feu/VLAN. Vérifier la redirection HTTP et les certificats sur chaque lecteur.

### S02 — P1 — Prise du premier compte par le premier client réseau

**Sources :** `apps/api/src/index.ts:71-76`, `compose.yaml:50`, `docker/nginx-player.conf:15`.

Tant que la base ne contient aucun utilisateur, `POST /auth/setup` attribue le rôle superadministrateur sans secret d’amorçage ni restriction à localhost. Tout client pouvant joindre le service pendant cette fenêtre peut prendre le contrôle initial. Le proxy du lecteur expose lui aussi cette route. Le verrou transactionnel évite deux comptes initiaux concurrents, mais n’authentifie pas le premier demandeur.

**Confirmation :** lecture du chemin complet d’initialisation ; aucun compte créé sur l’instance examinée. La documentation prévient déjà d’effectuer cette étape sur un réseau de confiance, sans imposer techniquement cette condition.

**Correction :** secret d’installation aléatoire à usage unique fourni localement, ou initialisation par CLI/bind localhost avant ouverture réseau. Refuser les routes d’administration sur le proxy des lecteurs.

### S03 — P1 — Dépendance Zod signalée vulnérable

**Sources :** `apps/api/package.json`, `package-lock.json`, `apps/api/src/validation.ts:7-14`.

`npm audit --json` signale Zod **3.25.76**, gravité **high**, avis [GHSA-mrhx-c7xc-m3w5](https://github.com/advisories/GHSA-mrhx-c7xc-m3w5) : consommation mémoire excessive lors de la validation de collections trop volumineuses. L’audit indique une correction à partir de 4.6.6 et propose 4.6.7, avec changement majeur.

**Confirmation :** dépendance installée et audit npm concordants ; 1 high, aucun autre avis rapporté. Les scènes, programmes, planifications et événements valident des tableaux. Ces routes exigent un compte ou un jeton lecteur et le corps JSON est limité à 2 Mio : l’exposition applicative est donc plus restreinte que le score générique de l’avis. Aucun épuisement mémoire n’a été tenté.

**Correction :** migrer vers une version corrigée après vérification de compatibilité, ajouter des contrôles précoces de taille des collections et des tests de rejet à mémoire bornée. Éviter `npm audit fix --force` sans revue.

### S04 — P1 — Le compte PostgreSQL applicatif est superadministrateur

**Sources :** `compose.yaml:7,24`, `apps/api/src/db.ts:2`.

L’utilisateur créé par `POSTGRES_USER` est réutilisé par l’API. La requête de lecture `SELECT rolsuper,rolcreatedb,rolcreaterole FROM pg_roles WHERE rolname=current_user` renvoie **true, true, true** sur l’instance locale.

Une compromission de l’API ou une future injection SQL disposerait donc de tous les droits PostgreSQL, au-delà des tables nécessaires au service. Cela n’établit pas l’existence actuelle d’une injection SQL ; les requêtes examinées utilisent des paramètres.

**Correction :** séparer le compte de migration du compte d’exécution ; créer un rôle non-superuser, sans création de rôles/bases, avec seulement les droits requis. Adapter les migrations exécutées actuellement au démarrage. Tester l’installation neuve et la migration des volumes existants.

### S05 — P1 — Imports sans quotas globaux ni confinement des conversions

**Sources :** `apps/api/src/index.ts:47-48,85-97`, `apps/api/src/pdf-imports.ts:9-26`, `apps/api/src/video-imports.ts:13-31`, `docker/Dockerfile:17-32`, `compose.yaml:18-42`.

Un éditeur peut multiplier les imports de 500 Mio ou les PDF de 25 Mio : aucune limite d’espace total, de file d’attente ou de simultanéité des uploads n’est appliquée. Le tampon PDF est intégralement en mémoire. Les limites par fichier et le traitement séquentiel des conversions ne bornent pas les uploads simultanés, le volume cumulé ou la mémoire des décodeurs.

FFmpeg et Poppler s’exécutent dans le conteneur API, avec son utilisateur, son environnement hérité (incluant DATABASE_URL) et son volume médias. Aucune limite Docker mémoire/CPU/PID n’est configurée. Un fichier complexe ou des imports répétés peuvent affecter la disponibilité ; une éventuelle faille du décodeur aurait accès aux ressources de l’API. **Aucune faille de décodeur ni lecture arbitraire de fichier n’a été démontrée.** FFmpeg limite déjà les protocoles à `file,pipe`, ce qui réduit le risque réseau.

**Correction :** quotas de stockage et de file par installation/utilisateur, limite de conversions et uploads, seuil d’espace libre, limites cgroups, taille maximale des sorties ; worker isolé sans identifiants DB privilégiés, accès disque minimal et réseau restreint. Conserver les délais et limites de pages/durée existants. Tester avec fichiers synthétiques bornés, sans saturer la production.

### S06 — P2 — Chargements réseau arbitraires via les fonds de scène

**Sources :** `apps/api/src/validation.ts:7-8`, `apps/admin/src/SceneEditor.tsx:17-19`, `apps/player/src/render.tsx:13,27`.

Les fonds sont des chaînes libres de 100 caractères directement affectées à la propriété CSS `background`. Une valeur `url(https://security-probe.invalid/pixel)` passe le schéma. La prévisualisation administration tente effectivement cette requête dans Chromium. La requête a été interceptée et annulée par le test : aucun appel au domaine externe n’a été envoyé.

Un éditeur peut ainsi provoquer du suivi externe ou des requêtes GET depuis le navigateur de l’utilisateur qui ouvre la scène. Pour atteindre un lecteur, la scène doit être publiée/affectée. Cela contourne l’intention de contenus locaux et le contrôle des URL des médias. Il ne s’agit pas d’une preuve de XSS, de lecture de réponse cross-origin ou de vol de jeton ; les restrictions du navigateur continuent de s’appliquer.

**Correction :** valider des couleurs au format strict, utiliser `backgroundColor`, et instaurer une CSP limitant images/médias aux origines et schémas réellement requis (`self`, `blob:`, `data:` selon usage). Test de non-régression sur une scène et un élément.

### S07 — P2 — En-têtes Nginx perdus sur les pages HTML

**Sources :** `docker/nginx-admin.conf:11-13,26-33`, `docker/nginx-player.conf:11-13,28-40`.

Les blocs `location /`, `/assets/` et `/sw.js` redéfinissent `add_header Cache-Control`. Avec Nginx 1.28, cela supprime l’héritage des `add_header` du niveau serveur. Les protections `X-Frame-Options`, `Referrer-Policy` et `X-Content-Type-Options` ne sont donc pas envoyées sur ces réponses.

**Preuve :** `curl -sI http://127.0.0.1:8080/` et équivalent 8081 : ces trois en-têtes sont absents. Aucune CSP n’est configurée non plus. L’interface peut être encadrée ; l’impact authentifié du clickjacking dépend notamment de SameSite et du site attaquant. Les en-têtes de l’API sont un chemin distinct.

**Correction :** inclure les en-têtes communs dans chaque location concernée ou supprimer les redéfinitions conflictuelles ; ajouter `frame-ancestors 'none'` si aucun encadrement n’est requis. Vérifier HTML, assets, erreurs et lecteur, sous HTTP et HTTPS.

### S08 — P2 — Pas de révocation administrative des sessions utilisateur

**Sources :** `apps/api/src/index.ts:37,77-82,197`.

Les sessions durent sept jours. Le logout ne supprime que la session présentée. Il n’existe pas de route pour changer/réinitialiser un mot de passe, désactiver un compte ou révoquer toutes ses sessions. Modifier le rôle agit dès la requête suivante, mais ne supprime pas l’accès en lecture ni la possibilité de se reconnecter avec un mot de passe compromis.

**Impact :** réponse à incident incomplète après vol de compte ; intervention SQL nécessaire pour couper les accès proprement.

**Correction :** désactivation de compte, changement de mot de passe avec réauthentification et révocation globale, journalisation de ces opérations. Test avec deux sessions simultanées. En attendant, procédure opérateur explicite de révocation en base.

### S09 — P2 — Identité réseau des clients perdue derrière Caddy

**Sources :** `docker/Caddyfile`, `docker/nginx-admin.conf:21`, `docker/nginx-player.conf:21`, `apps/api/src/index.ts:26,47,77`.

Dans la topologie HTTPS, Nginx reçoit la connexion de Caddy puis remplace `X-Forwarded-For` par son `$remote_addr`, donc l’adresse de Caddy. L’API fait confiance à un seul saut. Les clients d’un même proxy partagent alors les quotas IP, dont dix tentatives de connexion par minute et le quota global de 600 requêtes/minute.

**Impact :** un client peut consommer le quota des autres ; un parc de lecteurs peut provoquer des 429 collectifs. Les journaux perdent aussi l’adresse réelle. Conclusion de configuration ; le profil Caddy n’a pas été démarré pendant la revue.

**Correction :** définir précisément les proxies approuvés et normaliser l’IP client à chaque saut ; ne jamais accepter aveuglément un X-Forwarded-For externe. Combiner des limites IP, compte et appareil. Vérifier deux clients distincts et une tentative d’usurpation d’en-tête.

### S10 — P2 — Journal de sécurité incomplet et amplification des événements lecteur

**Sources :** `apps/api/src/index.ts:36,77-82,163,176-182,197`.

Les événements ne couvrent pas les échecs de connexion et changements de rôle. Les commandes de lecteur disposent déjà d’un événement `screen.command`. Les logs HTTP ne remplacent pas un journal métier attribué à un acteur. À l’inverse, un lecteur authentifié peut soumettre jusqu’à 100 événements par appel, avec 2 000 caractères par message ; seule la limite générique de requêtes et la purge à 30 jours bornent cette croissance. Le nom d’événement est libre, même si `screen_id` distingue sa provenance.

**Impact :** investigation difficile et consommation disproportionnée du stockage par un lecteur compromis. Pas de test de saturation effectué.

**Correction :** événements de sécurité structurés, types réservés séparés des événements lecteurs, quota d’événements/octets par appareil, rétention et alertes, stockage de journal protégé contre les modifications applicatives. Ne jamais enregistrer mots de passe, cookies ou jetons.

## Protections constatées

- Scrypt avec sel aléatoire et comparaison constante ; minimum de douze caractères à la création.
- Sessions et jetons aléatoires de 32 octets, uniquement leurs empreintes en base ; cookie HttpOnly et SameSite=Strict.
- Requêtes SQL paramétrées dans les chemins examinés, contrôles de rôle côté serveur ; publication réservée admin/superadmin.
- Neuf routes sensibles testées sans authentification renvoient 401 : users, media, scenes, screens, schedules, events, imports/pdf, imports/video, players/me/manifest.
- Origine étrangère sur logout sans cookie : 403. Les proxies écrasent X-Forwarded-Host ; pas de contournement CSRF démontré dans la topologie standard.
- Jumelage limité dans le temps, confirmation admin, secret d’appareil et consommation transactionnelle ; accès média des lecteurs restreint à leur manifeste.
- React rend les textes comme texte ; pas d’insertion HTML arbitraire trouvée dans les chemins examinés.
- Noms de fichiers stockés sous identifiants générés, formats limités, aucune commande shell construite à partir du nom fourni ; conversions via execFile.
- Vérification SHA-256 avant activation des médias ; URL de média contrainte à un chemin local ; révocation en ligne du lecteur efface son état local.
- API exécutée en utilisateur non-root ; ni port PostgreSQL ni port API publié directement ; pas de montage du socket Docker.
- Initialisation du secret DB aléatoire avec umask 077 ; `.env` ignoré par Git et Docker. Recherche ciblée de signatures de clés dans apps/packages/docker/scripts sans correspondance ; ce contrôle n’est pas un scan exhaustif de l’historique Git.
- Sauvegardes avec permissions restrictives et contrôles d’intégrité. Les checksums ne prouvent pas l’origine d’une archive : seules les sauvegardes fiables doivent être restaurées, puisque restauration SQL et extraction s’effectuent avec des privilèges élevés.

## Vérifications et limites

- `npm test` : **32 tests réussis** (5 API, 9 lecteur, 18 shared). Ils ne constituent pas une couverture complète des rôles/IDOR/CSRF.
- `npm audit --json --cache /tmp/scenzly-npm-cache` : **1 high (Zod)**. Les dépendances système des images Docker ne sont pas couvertes par npm audit.
- Test navigateur avec API simulée, code de prévisualisation compilé et schéma réel : fond URL accepté, requête externe tentée puis bloquée par interception.
- Requêtes HTTP sans session et lecture seule des attributs du rôle DB. Aucune donnée métier modifiée, aucun mot de passe lu, aucune charge volumineuse ou destructrice envoyée.
- Les conteneurs HTTP locaux exécutent une construction antérieure au dernier changement de thème ; les configurations Nginx concernées sont inchangées. Le test de scène utilise la prévisualisation compilée du code examiné.
- Pas de scan CVE des images/OS (Trivy absent), de fuzzing des décodeurs, de test d’intrusion du LAN réel, de test de saturation ni de matrice d’intégration complète des quatre rôles pendant cette revue. Le profil HTTPS est analysé statiquement, pas validé dynamiquement ici.
- Le cache hors connexion conserve intentionnellement des contenus tant que l’appareil est déconnecté ; une révocation serveur n’efface pas à distance un appareil hors ligne. Les jetons du lecteur sont accessibles à son profil navigateur : prévoir kiosque, protection physique et chiffrement disque selon sensibilité.

## Ordre de correction proposé

1. HTTPS et amorçage protégé ; mise à jour Zod avec tests de migration.
2. Rôle PostgreSQL minimal, quotas d’import et isolation du worker.
3. Validation des couleurs, en-têtes/CSP, tests de navigateur correspondants.
4. Révocation des comptes/sessions, chaîne de confiance proxy et quotas par identité.
5. Journalisation de sécurité, scan régulier des images et tests de sécurité en CI.

Après corrections, reproduire chaque constat et compléter les tests authentifiés sur une installation jetable avant de considérer les points clos.
