## Content limits and existing data

These limits concern JSON metadata and scene text, not image/video bytes:

- Maximum scene/schedule/program-items document: 256 KiB, measured using PostgreSQL's stored JSON text representation.
- Maximum collection storage: 8 MiB each for scenes, program items and schedules. Program admission includes a conservative allowance for names and other metadata returned by lists.
- Maximum 1,000 records in each collection and 1,000 retained publication versions globally.
- Maximum publication snapshot: 2 MiB; total retained snapshot storage: 64 MiB.
- Maximum manifest: 8 MiB, with a 4 MiB published-program preflight budget and a 256 KiB per-device schedule budget.

Writes reserve capacity under the same database advisory transaction lock as publication and deletion. Read budgets are checked in the same SQL snapshot as the returned rows, before JSON reaches Node. Only the scalar byte budget is materialized; oversized collections are not copied into a JSON aggregate. PostgreSQL formatting overhead is included in admission.

Nothing is automatically deleted. Over-budget datasets reject new growth with HTTP 413. Reducing an existing document to the per-document limit or deleting unused content allows recovery. For an oversized scene collection, the UI displays up to 1,000 summaries and fetches the selected scene's full contents before editing, so saving a summary cannot erase its elements. The API also supports `GET /api/v1/scenes?summary=true&offset=1000` for subsequent summary pages and `GET /api/v1/scenes/:id` for an individually bounded legacy scene (4 MiB ceiling). Unusually large legacy program/schedule collections can be reduced through their existing authenticated update/delete endpoints; no database reset is necessary.

Media storage remains controlled separately by `MEDIA_QUOTA_MB`. Existing snapshots continue to protect their referenced media; the update does not silently prune historical publications.

## Upgrade

Back up the installation using the existing backup procedure, then:

```sh
git pull
docker compose build --pull
docker compose up -d --wait
```

Use the same Compose modes/files as the existing installation. A plain `docker compose pull` is insufficient for the rebuilt PostgreSQL and optional Caddy services; the images must be built. The Caddy data volume and local certificate authority are preserved. No PostgreSQL major-version migration or collation/library-family change is introduced.

An older browser cache entry may remain until its previous one-hour lifetime expires or the browser cache is cleared. The server cannot retrospectively retract bytes already downloaded. New API responses are not stored in the HTTP cache. Offline display media remain intentionally available until a revoked device reconnects.
