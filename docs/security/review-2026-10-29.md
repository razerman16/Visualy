# Security review — 29 October 2026

Audited source: `5369d54fbac9dccc7a682be218f9d17bd75bb27e`. This is an assessment, not a remediation release. The findings below remain open at this commit.

The subsequent [correction report](fixes-2026-10-29.md) describes the implementation, upgrade procedure and remaining package advisories. This audit remains a record of the original vulnerable commit.

The review covered authentication, authorization, installation, database privileges, media uploads and conversion, publication, player pairing and offline storage, browser rendering, reverse proxies, Docker isolation, deployment scripts, dependencies and CI. Existing application containers and user data were left untouched. Integration tests used disposable installations.

### A01 — Encoded paths bypass upload admission controls

**Source:** `apps/api/src/upload-guard.ts:12`, controls at lines 13–20; proxy behavior in `docker/nginx-admin.conf:17`.

The hook selects upload requests using a regular expression against the raw `req.url`. Fastify resolves percent-encoded characters to the registered route, while the hook does not. Nginx's `proxy_pass` without a URI preserves the encoded request URI.

Reproduction used the actual upload guard and a real disposable Nginx 1.30 proxy. An authorized identity and pending-job database count were simulated; handlers only recorded execution. With a 1 MiB media quota, the normal route rejected the request before handler execution, while its encoded equivalent reached the handler:

| Normal path: HTTP 507 | Encoded path: HTTP 200 from fixture handler |
| --- | --- |
| `/api/v1/media` | `/api/v1/%6dedia` |
| `/api/v1/imports/pdf` | `/api/v1/imports/%70df` |
| `/api/v1/imports/video` | `/api/v1/imports/%76ideo` |

This bypasses the upload-specific rate limit, concurrent upload limit, pending import limit, media storage quota and minimum free-space reservation. Authentication, role checks, individual file-size limits and general request limits still apply. An editor could exhaust persistent storage or overwhelm the import queue. No disk exhaustion was attempted.

**Remediation:** attach the admission check directly to each upload route, or select routes using Fastify's canonical `req.routeOptions.url`. Add regression tests for all three encoded paths, asserting that the handler is not reached when quota/admission fails. Preserve authorization before body consumption.

### A02 — Vulnerable optional Caddy image and incomplete image scanning

**Source:** `compose.https.yaml:15`; `.github/workflows/security.yml:27`.

The configured image is `caddy:2.10-alpine`. The locally available image inspected here contains Caddy 2.10.2, Go 1.25.0 and Alpine 3.22.3. Trivy reports 102 HIGH/CRITICAL package/advisory occurrences, 101 with a fixed version announced. These are not 102 demonstrated exploits.

Two alerts concern the TLS server surface used by this configuration:

- [CVE-2026-32283](https://avd.aquasec.com/nvd/cve-2026-32283): TLS 1.3 KeyUpdate processing can deadlock and consume resources; the advisory lists Go 1.25.9 / 1.26.2 as fixed versions.
- [CVE-2026-56862](https://avd.aquasec.com/nvd/cve-2026-56862): repeated KeyUpdate messages can force indefinite key derivation; the advisory lists Go 1.25.13 / 1.26.6 / 1.27.0-rc.3 as fixed versions.

The affected runtime is confirmed by image inspection, but no TLS denial-of-service exploit was run. Alerts involving unused mTLS, FastCGI, Windows or other features are not assumed exploitable. Caddy is not started in the default HTTP deployment, so this finding applies when an HTTPS override is enabled.

CI currently scans only API, converter, admin and player images. Both Caddy and PostgreSQL are omitted, which allows their alerts to escape the configured gate. The local PostgreSQL image also has fixable alerts, many in Go libraries embedded in `gosu`; those do not establish a remotely exploitable PostgreSQL server vulnerability.

**Remediation:** select and validate an updated Caddy image with a corrected Go runtime, rescan it and run the HTTPS/custom-port recipe. Refresh and rescan PostgreSQL as well. Include both infrastructure images in CI, retain complete scan results, and track unfixed findings separately from the fixable-vulnerability gate. Recheck the actual pulled image digest; a mutable tag is not evidence of the contents currently installed.

### A03 — Persistent JSON and aggregate response sizes are unbounded

**Source:** `apps/api/src/validation.ts:9`, `apps/api/src/index.ts:140`, `:143`, `:156`, `:160`, `:43`, `:48`; API memory limit at `compose.yaml:69`.

The request size and per-document element limits do not bound accumulated stored content. An editor can repeatedly create scenes. Listing scenes loads every document into Node without pagination or a cumulative byte limit. Publication collects referenced scenes into a single version, and the player manifest aggregates published programs. Media authorization for devices also reconstructs the manifest.

Bounded checks against the real validation schemas accepted a scene containing 200 text elements of 10,000 characters each: approximately 2.014 MB, below the 2 MiB request limit. Three hundred such scenes represent approximately 604 MB of JSON before object and serialization overhead, against a 768 MiB API container limit. An editor can create and list these without administrator publication. A valid 500-scene program can aggregate approximately 1.007 GB, exceeding the runtime string-size limit as well as the container budget.

Only one synthetic scene and a small playlist were constructed to verify schema acceptance and calculate aggregate sizes. No large database, memory exhaustion or application crash was induced. The exact failure threshold depends on content and runtime overhead.

**Remediation:** enforce transactional count/byte budgets on scenes and retained versions; return paginated metadata lists with detail endpoints; cap aggregate publication and manifest sizes before materializing them. Check device media membership without reconstructing the complete manifest for each download. Resource limits and HTTP body limits alone do not resolve cumulative amplification.

### A04 — Administrative media survive logout in the browser HTTP cache

**Source:** `apps/api/src/index.ts:125`.

Media responses authenticated by an administrator's session use `Cache-Control: private, max-age=3600`. `private` prevents shared-cache reuse but allows the browser's own cache. A fresh cached response can therefore be read without contacting the API after logout or server-side revocation.

A Chromium probe against an ephemeral server reproducing the exact cache policy and an HttpOnly session cookie returned the protected content with HTTP 200 after cookie removal, without a new server request. A forced uncached request returned 401. This verifies the browser behavior of the policy; it was not a production-data extraction test.

The impact is confined to data already downloaded in the same browser profile, potentially for one hour. It is separate from the intentional offline cache of a paired display.

**Remediation:** send `Cache-Control: no-store` for administrative media and sensitive session API responses. Retain player offline behavior through its explicit Cache API. Test load → logout/revoke → re-read in a real browser. Existing cached copies may persist until expiry or explicit local cache clearing after deployment of the fix.

### A05 — The administrative UI retains data after HTTP 401

**Source:** `apps/admin/src/api.ts:24`; `apps/admin/src/App.tsx:39`, `:48`.

The API client converts 401 into a generic error. Refresh displays that error but retains the user and loaded collections. State cleanup occurs on successful explicit logout, not when the session expires or is revoked remotely.

A Chromium probe loaded the real administration bundle with simulated API responses, loaded a private scene, switched the API to 401, then clicked Refresh. The authentication error appeared, but the private scene and account identity remained visible and no login form appeared. Server authorization was not bypassed; further requests were rejected.

**Remediation:** represent authentication errors explicitly, clear sensitive state and open editors/modals on 401, and return to login. Propagate logout between tabs. Distinguish session rejection from temporary network/server failures so those failures do not unnecessarily discard drafts.

## Additional hardening and known deployment risks

- **Login timing:** `apps/api/src/index.ts:82` skips password verification for missing or disabled accounts. Local measurements of the real password verifier took approximately 34–50 ms on a wrong password; the missing-account branch performs no scrypt. Account enumeration by HTTP timing was not demonstrated. Verify a precomputed dummy hash for unknown/disabled accounts while keeping generic responses and rate limits.
- **Default HTTP:** transport is unencrypted by explicit product choice. An attacker who can intercept or modify LAN traffic can obtain credentials, sessions and player tokens. HTTPS remains optional; this review does not change that default. Use the documented HTTPS mode after addressing A02 where the network cannot be trusted.
- **Offline players:** a physically accessible browser profile contains a persistent player token and downloaded media. Server revocation cannot erase a disconnected device; cleanup occurs on reconnection. This is an existing offline-mode limitation.
- **System packages:** the API/converter have HIGH/CRITICAL alerts with no fixed package version reported by the scan database. Isolation reduces exposure but does not prove those alerts harmless.
